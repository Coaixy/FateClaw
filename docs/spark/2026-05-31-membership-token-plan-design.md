# FateClaw 会员体系方案：Token Plan

日期：2026-05-31

## 结论

会员体系建议做成 **Token Plan**，不要做 Skill 订阅、创作者整包付费或内容市场抽成。

核心模型是：用户按月购买会员，获得一组月度 Token 权益、模型使用权益和服务优先级；超出会员权益后继续走钱包余额按量扣费。钱包仍然存在，负责充值、超额用量、补差价和赠送余额。

这套方案的重点不是“卖内容”，而是把用户对 AI 调用成本的预期固定下来，让用户知道每个月大概能用多少、能用什么模型、超出后怎么扣。

## 设计原则

1. **会员只围绕模型资源收费**
   Skill、Bundle、创作者发布内容都保持免费订阅关系，不再出现单个 Skill 售价、创作者整包售价、内容抽成。

2. **钱包和会员并存**
   会员给月度权益；钱包给余额兜底。用户没有会员也能充值按量使用，会员用户超额后也能继续用，不会突然中断。

3. **Token 权益按“价值额度”结算，不按裸 Token 数硬切**
   不同模型成本差异大。会员应该发放“月度权益额度”，内部可以用软妹币或模型成本额度折算，而不是简单承诺所有模型都给同样 Token 数。

4. **权益清晰，不做复杂叠加**
   第一版只做月度会员，不做年费、不做家庭组、不做创作者权益、不做任务包。后续等真实用量稳定后再扩展。

5. **超额透明**
   用户在 UI 上看到本月会员权益已用、剩余额度、钱包余额、本月预计扣费。超额扣钱包前不需要每次确认，但余额不足时要清晰提示充值。

## 推荐会员层级

建议第一版只上 3 档，外加无会员的按量用户。

| 层级 | 目标用户 | 建议权益 | 超额规则 |
| --- | --- | --- | --- |
| Free | 新用户、低频体验 | 每日少量免费额度或注册送一次性赠送余额 | 用完后走钱包 |
| Plus | 普通爱好者 | 月度基础权益额度，适合日常聊天、排盘解释、轻量任务 | 超额按钱包原价扣 |
| Pro | 高频用户 | 更高月度权益额度，允许更长上下文、更高并发或更高任务频率 | 超额按钱包折扣价扣 |
| Max | 可选，不建议首发 | 给重度用户或内测用户，额度更大，服务优先级最高 | 需要真实成本数据后再定 |

首发建议只开放 `Free / Plus / Pro`。`Max` 可以先在文案和后台保留概念，但不在前台售卖。

## 权益构成

每个会员档位由以下字段组成：

- `monthly_credit_coins`：每月赠送的会员权益额度，按软妹币记账，但只能用于模型 Token 消耗。
- `included_model_tiers`：可使用的官方模型层级，例如基础模型、增强模型、高级模型。
- `platform_fee_discount`：自配模型平台服务费折扣，例如 Plus 无折扣，Pro 8 折。
- `context_limit_policy`：上下文窗口上限策略，例如 Free 限低，Plus 标准，Pro 更高。
- `concurrency_limit`：同时运行的 AI 会话或任务数量。
- `priority_level`：排队优先级，避免高峰期所有用户体验一样。
- `monthly_reset_policy`：会员权益按自然月或订阅周期重置，不提现、不转赠，过期清零。

这里的 `monthly_credit_coins` 应该和现有钱包余额分开记账。钱包的 `purchased_coins / bonus_coins` 是用户资产；会员权益是订阅期内的服务额度，不应混入可提现或可长期累积的余额。

## 建议定价结构

下面是产品结构示例，不是最终价格。价格应在接入真实模型成本后再定。

| 档位 | 月费定位 | 月度权益 | 模型权限 | 服务费 | 适合场景 |
| --- | --- | --- | --- | --- | --- |
| Free | 0 元 | 新用户赠送或每日少量权益 | 基础模型 | 原价 | 试用、低频排盘 |
| Plus | 低门槛 | 约等于月费 1.2-1.5 倍的模型权益 | 基础 + 标准模型 | 原价 | 日常聊天、常规分析 |
| Pro | 高频 | 约等于月费 1.5-2 倍的模型权益 | 标准 + 高级模型 | 8-9 折 | 高频对话、长上下文、任务 |

会员不是无限使用。不要写“无限 Token”或“无限聊天”。更好的表达是“每月含 X 软妹币模型权益，超出后按量计费”。

## 扣费顺序

模型调用完成后，根据实际输入/输出 Token 计算成本，然后按以下顺序抵扣：

1. 会员月度权益额度
2. 钱包赠送余额
3. 钱包充值余额
4. 如果余额不足，进入欠费/暂停使用提示

这样用户体验最直观：先用会员，再用赠送，再用自己充值的钱。

会员权益只抵扣模型 Token 成本和平台服务费，不抵扣未来可能出现的实体商品、人工服务或其它非模型成本。

## 数据模型建议

第一版建议新增三类表，不复用旧 `plans` 或旧用户订阅字段。

### membership_plans

会员计划定义表，后台可配置。

关键字段：

- `id`
- `code`：`free`、`plus`、`pro`
- `name`
- `price_coins`
- `billing_period`：首发只支持 `monthly`
- `monthly_credit_coins`
- `included_model_tiers`
- `platform_fee_discount_bps`
- `context_limit_tokens`
- `concurrency_limit`
- `priority_level`
- `enabled`
- `created_at`
- `updated_at`

### user_memberships

用户当前会员状态。

关键字段：

- `id`
- `user_id`
- `plan_code`
- `status`：`active`、`expired`、`cancelled`
- `started_at`
- `current_period_start`
- `current_period_end`
- `auto_renew`
- `created_at`
- `updated_at`

### membership_credit_grants

会员周期权益额度。它类似赠送余额，但来源和过期规则更严格。

关键字段：

- `id`
- `user_id`
- `membership_id`
- `plan_code`
- `amount_coins`
- `remaining_coins`
- `period_start`
- `period_end`
- `status`：`active`、`exhausted`、`expired`
- `created_at`
- `updated_at`

如果后续希望统一余额扣减逻辑，也可以把会员权益做成现有 `balance_grants` 的新来源 `membership`。但第一版建议独立表，原因是会员权益不是钱包资产，财务语义更清楚。

## API 建议

第一版 API 保持小范围：

- `GET /api/membership/plans`：列出可购买会员计划
- `GET /api/membership/me`：当前会员状态、周期权益、剩余额度
- `POST /api/membership/subscribe`：开通或升级会员，先用钱包余额支付
- `POST /api/membership/cancel-renewal`：取消自动续费
- `POST /api/admin/membership/plans`：后台维护计划

不建议复活 `/api/billing/activate`。会员域应该单独叫 `membership`，避免和钱包、按量计费混在一起。

## 前端体验

需要三个入口：

1. **钱包页**
   展示会员权益剩余、本月 Token 消耗、钱包余额、超额扣费规则。

2. **会员页**
   展示 Free/Plus/Pro 三档权益对比，重点展示“月度模型权益”“可用模型”“超额怎么扣”。

3. **模型设置页**
   当用户选择高级模型但当前会员不支持时，提示升级或走钱包按量高价扣费。第一版建议高级模型只允许 Pro 使用，避免 Free 用户误触高成本模型。

文案要避免“订阅 Skill”“购买创作者内容”“无限使用”。推荐用：

- “每月模型权益”
- “超出后按量扣钱包余额”
- “适合每日轻量使用”
- “适合长上下文和高频任务”

## 与现有系统的关系

现有系统已经有：

- 钱包余额：`purchased_coins / bonus_coins / reserved_coins`
- Token 用量统计：`daily_usage`
- 按 Token 结算：`settleBillingReservation`
- 充值订单：`recharge_orders`
- 模型单价和平台服务费配置

会员体系应当只接入结算环节：在 `settleBillingReservation` 计算出本次模型费用后，先尝试扣会员权益，再扣现有钱包余额。这样改动面最小，且不影响模型调用主流程。

## 边界规则

- 会员权益到期清零，不结转。
- 会员权益不可提现、不可转赠、不可给 Skill 或 Bundle 定价。
- 取消自动续费不立刻取消权益，权益持续到当前周期结束。
- 升级会员可以立即生效，并补发差额权益；降级下周期生效。
- 余额欠费时，即使有会员也不能继续超额调用。
- 管理员可以给用户手动赠送钱包余额，但不建议手动改会员权益，避免对账混乱。

## 分阶段落地

### 第一阶段：只做会员权益抵扣

- 新增会员计划和用户会员表。
- 新增会员权益额度表。
- Token 结算时先扣会员权益，再扣钱包。
- 钱包页展示会员权益剩余。
- 会员页展示三档方案。

### 第二阶段：做自动续费和升级补差

- 支持会员到期前自动从钱包扣月费续费。
- 支持 Plus 升 Pro 补差价。
- 支持后台查看会员分布和权益消耗。

### 第三阶段：做精细化模型权益

- 按模型 tier 控制可用模型。
- Pro 提供更高上下文窗口和更高并发。
- 按真实成本数据微调权益额度和折扣。

## 不做事项

第一版不要做：

- Skill 单独定价
- 创作者整包售卖
- 创作者分成和提现
- 年费会员
- 家庭共享
- 无限 Token
- 复杂优惠券
- 多币种

这些都容易把系统重新带回复杂的内容付费或财务对账模型。当前更适合把会员做成清晰的 AI 资源套餐。

## 推荐默认方案

如果今晚只做一个产品决策，可以按这个方向定：

1. 会员叫“模型会员”或“Token 会员”，不叫“技能会员”。
2. 首发三档：Free、Plus、Pro。
3. Plus 面向日常使用，Pro 面向长上下文和高频任务。
4. 每档给月度模型权益额度，超出后走钱包。
5. Skill 和 Bundle 永久保持免费订阅关系，只服务于能力组织和分享。

这套方案最优雅的地方在于：用户理解成本低，现有钱包体系不用推翻，后端扣费链路改动集中，未来也能自然扩展到自动续费和模型分层。
